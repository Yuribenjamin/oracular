# oracular roadmap

Oracular is an on-device intent engine: your app learns when the user is ready, and nothing leaves the device. This roadmap says what we are building next and why, in order. It is a statement of priorities, not a schedule; items move when real integrations show they should.

## Principles that decide what gets in

- **Nothing leaves the device.** No feature may require a network call, a vendor, a device fingerprint, or cross-user data. Requests that need any of those get a polite no, however reasonable they sound.
- **Pure core, thin helpers.** The engine stays `(state, event) → state`. Anything with I/O lives outside the core, in documented patterns or small optional helpers.
- **Earn features from integrations.** A feature enters the roadmap when a real app needed it, not when it sounds useful. Two production integrations exist today; the third decides the shape of any framework binding.
- **Honest about the model.** The docs say what the engine can and cannot learn, and every number in a tuning table is generated from the engine's own math.

## Done: 0.3

The theme was **proof**. Both integrations had to invent the same thing, a shadow mode that records what the engine would have done; 0.3.0 made it a first-class workflow, so a team can run oracular silently, export a log, measure it offline, tune, and only then switch a reveal on. Everything below shipped in [0.3.0](/changelog):

1. **Recorder format and helpers.** `createRecord` and `createEndRecord` produce the lines of a versioned NDJSON log. Every record carries an install id (random, generated by the app, never derived from the device), keeps the raw event apart from the recorded decision, and says whether reveals were shadow or live at the time. The [Shadow mode](/guide/shadow-mode) guide has the format.
2. **`npx oracular replay`.** Replays a log through the engine under any config and reports, per intent and threshold, precision, recall, lead time from reveal to outcome, reveals per user, and a reliability table with a Brier score. Shadow periods only: a mixed log gets a warning, a live-only log is refused unless told otherwise.
3. **Per-episode saturation.** The n-th repeat of a signal in one episode adds `w × log2(1 + 1/n)`; `saturate: false` opts an intent out. State version 2, with its built-in migration.
4. **State robustness.** A fixture from every published version that must keep loading, and a fuzz test that feeds `deserialize` corrupt, truncated and tampered states.
5. **Packaging checks in CI.** `publint`, `@arethetypeswrong/cli`, `size-limit` with a hard budget, and the exact tarball file list, all inside `npm run check`; the Node matrix stays.
6. **Docs: [What oracular can and cannot learn](/guide/can-and-cannot-learn).**

## Now: 0.4

The theme is **learning that matches how people behave**. Items in priority order; the small ergonomics shipped first because nothing depends on them, and attribution landed after tune, so that a real log could be replayed with and without it.

1. **Cross-episode attribution.** Done. `IntentConfig.attribution` holds a closed episode for the outcome instead of recording a miss; an outcome inside the window credits each held episode by `2^(−age / halfLife)` with the complementary miss, so every episode still counts once and nothing is ever reversed; the window's end makes it a miss at that moment. Off unless set. State version 3 with its migration. See [Episodes & learning](/guide/concepts/episodes-and-learning#credit-across-episodes); whether a default is justified is a question for `tune` on real logs before 1.0.
2. **`npx oracular tune`.** Done. From a recorder log across users, grouped by install id: base rate → prior, per-signal lift → initial weights, half-life → the lowest Brier score over a grid scored by `replay`, spread of per-install base rates → prior strength. Emits a ready-to-paste config with sample sizes and a 90% interval per weight. The counts come from the engine itself. Population-seeded config, per-user correction on device; see [Shadow mode → Tune](/guide/shadow-mode#tune).
3. **Presets.** `presets.upgrade`, `presets.stuck`, `presets.churn`, `presets.willBuy`: plain config objects users can spread and override, with every knob explained. They are labelled as starting points and carry the sample size behind their numbers; two integrations is a thin base, and the label stays until it isn't.
4. **Small ergonomics.** Done: `validateConfig()` exported on its own; `ms.days(7)` and friends, a zero-cost units helper; a JSON Schema for the config, shipped as `oracular/config.schema.json`.

## Before 1.0

The theme is **promises we can keep**. 1.0 means the API and the state format are commitments.

1. **Stability policy, written down.** What is public API (every export from `index.ts`, the serialized state shape, and the recorder format), the deprecation window (one minor with warnings before removal), the `STATE_VERSION` guarantee (every bump ships a migration and fixture tests, as 0.3 did), and that validation error types and message shapes are part of the contract.
2. **Property-based tests.** Purity, monotone decay, the α/β invariant, serialize/deserialize identity, and `shouldReveal ⇒ lower ≥ threshold`, generated rather than hand-picked. The fixtures and the deserialize fuzz from 0.3 keep running against every release in between.
3. **A debug overlay.** A small framework-free widget showing predict and explain live for every intent. The shadow panels the integrations built are the prototype.
4. **One public case study with real numbers**, produced by `replay` on a production shadow log, and at least two production users referenced. A reproducible first one, on a public clickstream rather than a shadow log, is [Case study: a public clickstream](/guide/case-study-clickstream); the production one is still to come.
5. **Housekeeping.** Done in 0.3: GitHub Actions pinned by SHA, CodeQL and an OpenSSF Scorecard workflow, the publish-only-from-CI policy written down in SECURITY.md. What is left is keeping them green.

## After 1.0

- **Framework bindings** (`@oracular/react`, `@oracular/vue`) only once a third integration shows what the common hook is. Note for whoever builds them: do not end episodes on background or `visibilitychange`; a short app switch is not a session boundary. Flush persistence and let `episodeTimeout` close idle episodes.
- **Persistence helpers** for localStorage, AsyncStorage and IndexedDB, as separate tiny packages, if integrations keep rewriting them.
- **Playground upgrade.** Paste a recorder log, scrub a timeline, drag sliders for weights, half-life and threshold, and watch p and the lower bound move.
- **Project structure.** A GitHub organization and a second maintainer when a contributor shows up; GOVERNANCE.md says how.

## Considered and declined, for now

- **A population benchmark against a logistic model on public clickstream data.** A model trained on data oracular refuses to collect will win on precision. The meaningful comparison is against the rules a team would otherwise hand-write, on their own shadow log, which `replay` provides.
- **Performance benchmarks.** `observe()` runs in microseconds. Bundle size is the number that matters, and `size-limit` guards it.
- **Anything that phones home**, including opt-in telemetry about the engine itself.
